## 2. Product Definition

SafeFlux is an **AI-assisted process-safety verification system** for process/chemical engineers.

A process engineer provides or selects a process model and describes a proposed engineering change, for example:

> Increase production throughput by 30%.

SafeFlux then autonomously explores failure scenarios on a **digital simulation**, searching for unsafe combinations and operating boundaries.

The central principle is:

> **AI searches for danger → Simulator proves it → Engineer decides.**

SafeFlux is **not** an autonomous industrial controller and must not directly control a real plant.

## 4. Problem We Solve

When a process plant is modified, engineers must determine whether the change creates new unsafe conditions or invalidates existing safeguards.

A large amount of work can be repetitive:

- tracing affected equipment,
- enumerating deviations/failure modes,
- trying combinations of operating conditions,
- checking thresholds,
- repeatedly running calculations/simulations,
- checking whether safeguards act early enough,
- documenting evidence.

SafeFlux automates the repetitive **scenario-discovery and verification loop** while leaving safety judgment and approval to qualified humans.

## 6. Data Model Concept

SafeFlux distinguishes four data categories.

### A. Plant configuration — mostly static

Examples:

- tank capacity
- equipment limits
- normal operating ranges
- maximum allowable temperature/pressure
- pump capacity
- heater/cooling capacity
- safeguard configuration

This is entered/imported during setup and does not need constant manual re-entry.

### B. Current process state — dynamic

Examples:

- current flow
- current temperature
- current pressure
- current level
- cooling state
- valve position

For the hackathon this is generated by the **Python process simulator / telemetry generator**.

Future real product sources could include read-only connections to:

```text
Sensors → PLC/DCS → SCADA/Historian → OPC-UA/MQTT/API → SafeFlux
```

### C. Events/faults

Examples:

- cooling failed
- valve restricted
- sensor frozen
- shutdown delayed

These can be injected by the scenario engine into a cloned simulation state.

### D. Engineering change

Examples:

- increase throughput by 30%
- change pump capacity
- change operating target

The user describes the intended change; the system should avoid making the engineer manually test hundreds of numeric combinations.

## 7. Core User Workflow — LOCKED

```text
1. Engineer selects a plant/process model
           ↓
2. SafeFlux loads current/base configuration and state
           ↓
3. Engineer describes a proposed change
   Example: "Increase throughput by 30%"
           ↓
4. AI identifies affected equipment/variables
           ↓
5. Agent plans initial hazard scenarios
           ↓
6. Scenario engine creates cloned digital scenarios
           ↓
7. Deterministic simulator executes them
           ↓
8. Safety engine checks limits and safeguards
           ↓
9. Agent observes results
           ↓
10. If a case is near failure, agent generates harder/focused cases
           ↓
11. Search continues toward unsafe boundaries/counterexamples
           ↓
12. Root-cause/counterfactual checks are run
           ↓
13. SafeFlux presents evidence-backed failures and boundaries
           ↓
14. Engineer reviews and makes the final decision
```

The user should **not** sit and manually enter 100, 110, 120, 130, 140 repeatedly. The agent/search engine should explore that space automatically.

## 8. SafeFlux's Agentic Loop

```text
PLAN
  ↓
GENERATE / SELECT SCENARIO
  ↓
SIMULATE
  ↓
OBSERVE
  ↓
CHECK LIMITS
  ↓
SAFE? ──────────────→ record result
  │
  └─ near/fail
       ↓
ANALYZE
       ↓
GENERATE MORE INFORMATIVE TEST
       ↓
RE-SIMULATE
       ↓
COUNTEREXAMPLE / BOUNDARY / EVIDENCE
```

Important: the LLM does **not** invent physics values. It proposes experiments, interprets evidence, and explains results. Numerical truth comes from deterministic code.

## 9. Failure-Boundary Hunting

SafeFlux should do more than randomly generate scenarios.

Example:

```text
Cooling 100% → safe
Cooling 70%  → safe
Cooling 50%  → near limit
Cooling 40%  → unsafe
```

Then the search engine can narrow the boundary:

```text
45% → safe
42% → safe
41% → unsafe
```

The product may report an **observed simulated boundary** such as:

> Under the selected scenario, violations began when cooling fell below approximately X%.

This must always be presented as a result of the current simulation/model, not a certified real-world safety limit.

---

## 10. Root-Cause Investigation Philosophy

SafeFlux should not ask the LLM to guess a root cause.

It should use **counterfactual simulation**.

Example:

```text
Failure scenario found
       ↓
Restore cooling only → safe
Restore outlet only  → still unsafe
Reduce feed only     → safe
```

From this evidence SafeFlux can identify likely primary drivers and amplifying factors.

Desired evidence hierarchy:

1. deterministic simulation result,
2. threshold/invariant violation,
3. counterfactual experiment,
4. sensitivity/search evidence,
5. LLM explanation grounded only in the above.

## 13. Nebius + NVIDIA Integration — LOCKED PRINCIPLE

At least one NVIDIA open-source model must be used through the qualifying hackathon infrastructure.

For SafeFlux, the intended use is an eligible **NVIDIA Nemotron** model available in Nebius Token Factory at build time.

Do **not** permanently hard-code a model ID until Swayam's Token Factory account is approved and the available catalog is verified.

### Model responsibilities

The Nemotron-backed reasoning layer may:

- interpret the engineering change,
- identify affected components,
- plan initial scenarios,
- select useful next experiments,
- interpret simulator evidence,
- produce evidence-grounded causal explanations,
- summarize findings for the engineer.

The model must **not** be the source of:

- simulated temperature,
- simulated pressure,
- process equations,
- safety-limit truth,
- pass/fail threshold computation.

### Token Factory interface

Keep provider integration behind a clean abstraction such as:

```python
class ReasoningModel:
    def plan_scenarios(...): ...
    def select_next_test(...): ...
    def analyze_failure(...): ...
    def explain_evidence(...): ...
```

This lets us develop the rest of SafeFlux while Nebius access is pending and replace the temporary implementation cleanly once access is available.

Token Factory exposes an OpenAI-compatible API. Keep the API key in an environment variable such as `NEBIUS_API_KEY`; never commit it.
